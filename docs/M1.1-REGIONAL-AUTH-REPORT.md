## 1. Bug 1 — out-of-region alert acknowledgement

### Confirmed behaviour before the fix
`a.desai` (South supervisor) got **403** reading a West case and did not see the West alert on the
coordination dashboard — yet `POST /api/alerts/<west-alert-id>/acknowledge` returned **200** and persisted
`state = acknowledged`, `acknowledged_by = u-supervisor`, dropping the South supervisor's name onto a shared
West-region record.

### Root cause
`canAcknowledgeCoordination` in `server/src/domain.ts`:

```ts
if (!['bureau_officer', 'bureau_lead', 'supervisor'].includes(user.role)) return false;
const scope = getScope(user);
if (caseIds.some((id) => scope.metadataIds.has(id))) return true;
return user.role === 'supervisor' && Boolean(user.region);   // ← unconditional bypass
```

Any supervisor with a non-empty `region` was allowed to acknowledge any alert, because `getScope()` gives a
supervisor metadata for **their whole region** and the fallback ignored the alert entirely. The route in
`server/src/index.ts` passed only `case_ids_json`, so the function never saw the alert's institution region.

### Fix
The function now takes the alert itself and answers three questions in order:

```ts
export interface CoordinationAlertRef {
  institutionRegion: string | null;   // the alert's institution
  caseIds: string[];                  // every case the alert lists, not only visible ones
}

export function canAcknowledgeCoordination(user: SessionUser, alert: CoordinationAlertRef): boolean {
  if (!['bureau_officer', 'bureau_lead', 'supervisor'].includes(user.role)) return false;
  if (alert.institutionRegion && !inRegion(user, alert.institutionRegion)) return false;
  const scope = getScope(user);
  return alert.caseIds.some((id) => scope.metadataIds.has(id));
}
```

* role must be bureau officer, bureau lead or supervisor — **reviewers and administrators are refused**;
* the alert's institution must sit inside the caller's authorised region (`region` null keeps the existing
  national-oversight policy through `inRegion`);
* at least one listed case must be inside the caller's coordination scope, which is itself bureau- and
  region-limited, so a regional supervisor has no such scope outside their region. The blanket
  `supervisor && user.region` bypass is gone.

The route now joins the alert's institution and passes `{ institutionRegion, caseIds }`, and logs the region
in the denial entry (`alert_acknowledge_denied alert=… region=… role/bureau/region/grants`). Denial happens
before the `UPDATE`, so alert state, acknowledgement fields and business history are untouched — only the
separate security log is written. Personal notification acknowledgement (`POST /notifications/:id/acknowledge`)
is a different route and is unaffected.

## 2. Bug 2 — out-of-region transfer decisions

### Confirmed behaviour before the fix
A West PGRC lead requested transfer of a West case to RB. The South RB lead `l.verma` got **403** reading the
case, but `POST /api/transfers/<id>/decision` accepted **both** `accept` and `reject` with **200**; acceptance
moved ownership from PGRC to RB and bumped the case version.

### Root cause
`decideTransfer` in `server/src/service.ts` checked only the target bureau:

```ts
if (actor.role !== 'bureau_lead' || actor.bureau !== t.to_bureau) throw new AppError(403, …);
```

No region on the case, no shared guard on the route, and no `recordSecurityDenial`. `idSchema`-validated body
fields were irrelevant — the actor's *bureau* matched, so both branches wrote.

### Fix
New shared permission in `server/src/domain.ts`:

```ts
export function canDecideTransfer(user, c, transfer): boolean {
  if (user.role !== 'bureau_lead') return false;
  if (user.bureau !== transfer.toBureau) return false;
  if (c.institution_region) return inRegion(user, c.institution_region);
  return true;   // unresolved identity: the target bureau's own lead decides from intake
}
```

It is deliberately **not** an owning-bureau mutation guard — the receiving lead does not own the case yet.
It is enforced twice:

* **route**: a new `requireTransferDecision(user, transferId)` runs before `idempotent(...)` and therefore
  before either branch (or any idempotency record) is written, returning 403 with a security-denial entry;
* **service**: `decideTransfer` repeats the check before the reject/accept branches, so a direct service call
  cannot bypass the route.

Denied decisions leave the transfer `pending`, ownership, assignment and case version unchanged, and write no
`transfer_accepted` / `transfer_rejected` event.

## 7. Notes and deliberate limits

* A supervisor's coordination scope is region-wide, so **any West supervisor** may acknowledge a West alert
  (not only one named on the alert). That matches the current account policy; if acknowledgement should be
  narrower (e.g. designated owning-bureau leads only), that is a policy decision, not a code defect.
* Unresolved-intake cases carry no institution region, so `canDecideTransfer` lets the **target bureau's own**
  lead decide those transfers from intake. This preserves legitimate intake-queue transfers and cannot be used
  across regions, because a case without an institution has no other region to reach into.
* The security-denial log still has no read endpoint; the tests read the database file directly.
* The M1.1 suite is order-dependent on the shared `security-m1` instance fixtures only for convenience — it
  creates its own West institution cases, alert and transfers, so it can also be run standalone.
