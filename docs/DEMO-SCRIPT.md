# Three-minute demonstration

Environment: **start with fixture entry enabled** — `CASELINK_DEMO=true bash start.sh` — then open
http://localhost:8080. Everything on screen is synthetic; the yellow banner says so. Password for every demo
account: `caselink-demo` (published on the sign-in page only in this mode). Times are displayed in IST; the
API stores UTC.

> The **default** configuration (`bash start.sh`, no environment variable) requires sign-in and offers no
> account switcher, no `?as=` deep link and no password hint. Do not use it for this script. Demo mode only
> changes how you sign in — every permission rule below still applies (M1 regression 10f).

Keep the browser at normal desktop width with the seeded database freshly reset (`npm run seed`) so the
timings below match.

---

## 0:00 — The problem, in one screen (Sign in as `p.rao`, PGRC officer)

* My work: 30+ active cases in scope, overdue and approaching counters, and a triage row.
* Point at the header line: **PGRC · South region** — a role alone does not grant national access.
* The **Restricted** pill on an RB case row is the coordination boundary in one glance.

## 0:20 — Register the PGRC certificate complaint

1. **Register a case** → search `Vaigai` → choose **Vaigai Institute of Technology (AICTE-DEMO-1001)**.
   Mention: the fuzzy match is a *suggestion*; the permanent ID is what gets stored.
2. Category `Certificate / documentation`, channel `Email`, reference `PGRC/2026/0412`, summary: duplicate
   degree certificate not issued despite three reminders. Confirm **No deadline configured / DEMO-POL-30**
   is a labelled demo policy, not an official SLA.
3. Save. The toast confirms a server timestamp; the case number is generated by the server.

## 0:50 — The same institution from the other bureau (sign out → sign in as `s.iyer`, RB officer)

1. Register a similar complaint at the same institution, category certificate, reference
   `RB/COMP/2026/0187`.
2. Open **Coordination**. One alert exists for `AICTE-DEMO-1001` with bureaus **PGRC + RB**, listing both
   case references, category, status, owner role, deadline chip and last action time — and *no complaint
   text*. That is the "minimum coordination signal".

## 1:20 — Evidence and a human decision (sign in as `a.desai`, supervisor)

1. Open the same overlap. Show a **duplicate-report candidate** with its rule tags:
   `incident_period_overlap`, `same_category`, `topic_similarity` — each with the field it came from.
2. Then open the **infrastructure** complaint at the same college: it produces *no* duplicate candidate.
   Shared institution ⇒ coordination, not duplication.
3. Press **Review**, choose `Related issue`, write a reason, save. Then revoke it and show both cases are
   unchanged: same owner, same status, and both events in the timeline with actor and time.
4. Optionally demonstrate the grant path: the RB file shows "Summary restricted" until a lead grants
   access — a supervisor's role alone does not open a complaint file.

## 2:05 — Deadlines and the next action (sign in as `m.nair`, PGRC lead)

1. **My work → Overdue work**: a case with a breached DEMO deadline. Open it, show the deadline chip, the
   overdue reason and the priority factors.
2. Use **Record an action** → `Institute contacted`, pick status `Awaiting response`, set a response due
   date and the recipient role. Emphasise: awaiting response does **not** pause the disposal clock.
3. Then demonstrate the conflict path in one line: open the same case in a second tab, save in one tab,
   save the stale form in the other — 409, latest version shown, entered text preserved.

## 2:35 — Disposition, history and measured results (still `m.nair` or `l.verma`)

1. Record an authorised **Disposed** with a decision reference, then **Reopen** with a reason: previous
   outcome and original receipt time are preserved in the timeline.
2. **Reports**: totals reconcile with the Drill-down lists (current total, pending, overdue, transferred,
   escalated, disposal events); note the export only contains permitted rows and fields.
3. Close on the numbers: `npm run test:acceptance` → 21/21 (T01–T12 + 7 security checks), and
   `npm run bench` on 10,000 synthetic cases → list p95 145 ms, read p95 34 ms, mutation p95 643 ms,
   overlap alert 1.75 s. Say plainly that these are prototype measurements on synthetic fixtures.

## Two failure paths worth showing if asked (30 seconds each)

* **Settings → Simulate matching outage**: suggestions pause, the institution alert keeps working, cases
  still save, and the interface reports the available matching mode.
* **Settings/API demo endpoint `POST /api/system/inject-audit-failure`** (used by T12): a save that cannot
  write its audit event returns an error and leaves the case untouched — no partial ownership or action.

Never claim a government integration, an official service level, or real-world accuracy from these
synthetic fixtures.
