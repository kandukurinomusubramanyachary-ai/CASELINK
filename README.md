# CaseLink — SIH26264 institution complaint coordination (P0 prototype)

A working, runnable prototype of the CaseLink PRD (v1.0, 27 October 2026). It completes the P0 case
workflow from intake to recorded disposition, including the cross-bureau institution overlap alert and
a human-confirmed case link.

> **Demo environment.** Every institution, person, complaint, reference number and attachment is
> fictional and generated by the seed script. No AICTE system, connector, official service level or real
> personal data is used or implied. Case outcomes are entered by authorised staff; nothing is adjudicated
> automatically.

---

## 1. Quick start

```bash
cd caselink
bash start.sh               # installs deps / builds / seeds only if missing, then serves on port 8080
```

`bash start.sh` is idempotent and is the recommended way to start the app (run it with `bash` so a lost
executable bit after a snapshot restore cannot block startup): this sandbox drops installed
packages, build output and running processes between sessions, so the script re-checks each of them
before serving. `npm start` (build + serve) also works when `node_modules` is already present.

Then open **http://localhost:8080**. **The default configuration requires sign-in**, exactly as the PRD's
authenticated-officer workflow does: there is no auto-entry, no account switcher, no published demo password
and no `?as=` identity switching. Sign in on `#/login` with any account from the table below
(password for every synthetic account: `caselink-demo`).

### Demo (fixture) mode is opt-in

```bash
CASELINK_DEMO=true bash start.sh     # fixture entry: auto sign-in, header account switcher, ?as= deep links, password hints
bash start.sh                        # default: authenticated sign-in only (CASELINK_DEMO=false)
```

In demo mode the app drops you straight into **My work** as the bureau lead (`m.nair`), the header shows a
**Demo account** selector, `?as=a.desai#/coordination` switches the synthetic account, and `/api/auth/demo-login`
issues a session without a password. In every other configuration that endpoint returns **403** and the
interface behaves like a normal deployment. Demo mode changes *how you sign in*, never *what you may do*:
the permission rules below apply in both modes (regression 10f in `test/security-m1.mjs`).

## 3. What P0 delivers

| PRD area | Implementation |
| --- | --- |
| Officer sign-in and scoped access (AC01) | server-side sessions (HttpOnly cookie **or** `Authorization: Bearer` token, 8h expiry, so sign-in survives preview frames that block cookies), scrypt password hashes; scope = role + bureau + region + explicit case grants, computed per request and applied to lists, counts, pagination, detail, search, matching candidates, downloads and exports |
| Institution directory (FR01) | synthetic permanent IDs, internal UUID kept separate, reviewed alias table, fuzzy name matching returns *suggestions only*, unresolved intake held in a triage queue and excluded from overlap checks |
| Complaint entry (FR02) | server-generated UUID + readable case number, required-field and date validation, officer-in-bureau check, received time separate from import time, corrections recorded with before/after values |
| CSV import (FR03) | template download, per-row validation, preview batch, separate commit, 500-row cap, stable external reference required, duplicate/conflict classification (in-file and cross-batch), per-row transactions |
| Evidence (FR04) | PDF/PNG/JPEG only, magic-byte type validation, 5 × 10 MB per case, private storage, SHA-256 recorded, every download authorised through case access |
| Lifecycle and ownership (FR05–FR07) | single owning bureau, permitted-transition matrix, safe transfer (pending/reject/accept, atomic, idempotent), append-only action events, escalation flag that never replaces lifecycle state, reopening that preserves prior outcome and receipt time, optimistic version checks |
| Overlap detection (FR08) | ≥2 owning bureaus with active cases at one canonical institution → exactly one institution-level alert, recomputed on intake/reassignment/reopen, closed automatically when the active condition ends |
| Related-case suggestions (FR09) | deterministic P0 rules with ≥2 independent evidence signals, every reason shown with its source field; cross-institution duplicate candidates blocked; semantic ranking intentionally **not** enabled |
| Human relationship decisions (FR10) | Related issue / Duplicate report / Separate issues with a required reason; reviewer, evidence snapshot, rule version and time stored; revocation with reason; dismissed suggestions suppressed until evidence changes |
| Deadlines, notifications, reports (FR11–FR13) | versioned DEMO policies only (never an invented SLA), "No deadline configured" state, per-minute worker with dedupe keys, transparent priority factors, report definitions with drill-down reconciliation and CSV formula escaping |
| Consistency (section 8) | case change + action event + background job committed in one database transaction; worker retries idempotently; UI polls permitted updates every 10–15 s |

### Explicitly not built (out of P0 scope)

Semantic ranking, relationship graph, external email delivery, source-system connectors, public intake,
automatic adjudication or merging, institution guilt scores and mobile apps. Government integrations remain
disabled and are represented by an import adapter boundary only.

## 4. Architecture

```
web/            React 18 + TypeScript interface (Vite build, no runtime CDN dependencies)
  src/api.ts        typed API client
  src/screens/      My work, Institutions, Cases, Case workspace, Coordination, Alerts, Reports, Import, Settings
  src/components/   shared case table
server/
  src/schema.sql    relational schema (PostgreSQL-compatible shape, executed here on SQLite)
  src/domain.ts     case shape, scope/visibility engine, lifecycle transition matrix
  src/rules.ts      institution overlap (FR08), P0 suggestion rules (FR09), deadlines, priority
  src/service.ts    transactional mutations: create/update/assign/transfer/escalate/reopen/triage/grants/relationships
  src/worker.ts     job drain + 60s scheduled deadline/escalation scan, deduplicated notifications
  src/csv.ts        CSV parse/validate helpers, formula-injection-safe cell writer
  src/index.ts      HTTP API, authorisation checks, reports, import preview/commit, static SPA
  src/seed.ts       deterministic synthetic fixtures
test/           acceptance.mjs (T01–T12 + security), ui-smoke.mjs (Playwright), bench.mjs (10k scale)
docs/           screenshots, API reference, traceability, demo script, test results
```

**Stack note.** The PRD recommends React + TypeScript, a Node TypeScript API and PostgreSQL. This
prototype uses exactly that shape, with **SQLite (better-sqlite3) in place of PostgreSQL** because the
evaluation sandbox has no database server. SQL is ANSI-friendly (text UUIDs, ISO-8601 UTC timestamps,
partial indexes) and the data-access layer is isolated in `server/src/db.ts`, so moving to PostgreSQL is a
driver change plus migration files — not a redesign. This substitution is recorded in
[`docs/TRACEABILITY.md`](docs/TRACEABILITY.md#deviations).

Timezone: event timestamps are stored in UTC and displayed in Asia/Kolkata; every screen states this.

Proposed PRD targets — list/read p95 < 1.5 s, mutation < 2 s, overlap persistence < 5 s, dashboard refresh
< 10 s — are met at that scale **in this environment**. They are measured prototype results, not
claims about a production deployment.

The matching-evaluation protocol in PRD section 10 (60 complaints, 120 labelled pairs, precision/recall
against a rules baseline) was **not** executed; the P0 rule baseline it would compare against is
implemented, and the suggested P1 targets remain unproven. No real-world accuracy claim follows from
synthetic data.

## 6. Security and operational notes

### Permission model (Milestone 1)

Authority is always derived from the authenticated account, its bureau, its authorised region and approved
case grants — never from anything the client sends. Six questions are answered by shared functions in
`server/src/domain.ts` that both route handlers and service operations call:

| Question | Function | Who has it |
| --- | --- | --- |
| See coordination metadata | `canViewCoordinationMetadata` | same-bureau cases, cases at institutions where the bureau holds an active case, supervisor region, explicit grants |
| Read restricted contents | `canReadCaseContent` | bureau membership *or* an approved content grant |
| Modify a case | `canModifyCase` | read access **+** role **+** owning bureau **+** region; officers only their own assignments; supervisor, reviewer and administrator never |
| Upload evidence | `canUploadEvidence` | case-worker authority only — a read grant never allows uploads |
| Manage case access (grant/revoke) | `canManageCaseAccess` | owning bureau lead inside the region; supervisor inside oversight scope (including approved cross-bureau coordination); **never** officer, reviewer or administrator, and never because of the actor's own content grant |
| Acknowledge a coordination alert (shared state) | `canAcknowledgeCoordination` | authorised **against the alert itself**: the alert's institution must be inside the caller's region, and one of its cases must be inside the caller's coordination scope; bureau officer/lead/supervisor only, so reviewers and administrators never change shared acknowledgement state; `region` null keeps the existing national-oversight policy |
| Decide a transfer (accept/reject) | `canDecideTransfer` | a lead of the **target** bureau *and* regional authority over the actual case — deliberately not an owning-bureau guard, because the receiving lead does not own the case yet |
| Change administrative configuration | `canManageAdminConfig` | administrator only (worker tick, fault injection, matching mode, cross-bureau account directory) |

A content-read grant answers exactly one question: it never widens writing, uploading or access management.
Seeing coordination metadata never authorises granting access to contents. Unauthorised attempts return
**403**, leave grants, case records and business history untouched, and write a separate security-denial
entry (`/api/system/*` failures are logged the same way); authorised changes keep their audit trail.

### Operational notes

* No public role selector: the role is read from the authenticated account on the server for every
  request. A role or bureau supplied in a request body is ignored (test S02).
* Restricted coordination metadata (institution, case number, category, bureau, status, owner role, last
  action time) is separated from restricted content (complaint text, contact, attachments, history
  remarks). Notifications and overlap explanations never contain complaint excerpts.
* Inputs are validated with Zod and all SQL is parameterised. Complaint text is rendered as text, never
  as HTML.
* Relationship decisions, transfers, deadline changes and reopening require a reason; ordinary users
  cannot edit or delete history.
* Failure paths are implemented, not just documented: matching outage, notification failure, transaction
  failure (demo-only fault injection), expired session, stale record version.
* Secrets stay outside source control; the demo password is a fixture, not a credential pattern.

### Deployment gates before any real data

Hosting and data residency, field visibility, retention and deletion, backup and restore, evidence
scanning, and incident ownership all still need sponsor approval. Real complaint evidence requires a
scanning pipeline. The application event log supports traceability but is **not** a claim of immutable
infrastructure.
